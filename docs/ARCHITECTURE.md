# Architecture and decisions

Why Matchbook is built the way it is. Each section names the decision, the alternative, and the trade-off.

## 1. Where Matchbook sits

Ramp Bill Pay handles capture, coding, approvals, fraud signals, payment, and 3-way matching, and Ramp’s Agents for AP automate much of that. Matchbook starts when a match fails (or when the contract sweep finds a bill that passed but shouldn’t have) and ends when the bill is paid, voided, held, or handed to a person. It’s a resolution layer, not another capture or matching product.

It works on objects Ramp already has: bills, purchase orders, **item receipts**, **vendor agreements**, vendor bank accounts, **vendor credits**, and **PO change requests**. The tool names in the trace (`ramp.bills.get`, `ramp.purchase_orders.get`, `ramp.item_receipts.list`, `ramp.vendor_agreements.list`, `ramp.bills.list`, `ramp.vendors.bank_accounts`) are named after them.

## 2. Code owns the numbers; no model in the demo

| Concern | Owner |
|---|---|
| Line matching, variances, tolerances | `match.js` |
| Agreement price on the invoice date, escalation and notice | `match.js` (`contractPriceOn`, `pricesInForce`) |
| Duplicates, remit-to changes, lookalike domains, vendor-text instructions | `match.js` |
| Evidence | `retrieval.js` (BM25) |
| Root cause, resolution, approvals, drafts, reply verification | `resolve.js` |
| Grounding | `guard.js` |

**Alternative:** one LLM agent with tools that decides everything. It demos well and fails in finance: a model that gets 2,500 × $0.40 wrong sends a wrong legal claim to a supplier.

**Why no model at all in the demo:** the submission has to be shareable with no API keys, reproducible for graders, and honest. Every result on screen comes from deterministic code you can read and test. In production, a model writes explanation and email prose from the facts the engine allows, behind the same guard.

## 3. The grounding guard (`guard.js`)

`factsText(a)` builds the allowed facts from engine values only: amounts, unit prices, percentages, terms, document IDs, clauses, history, bank last-4s. It deliberately excludes the drafts themselves, so the check isn’t circular. `checkGrounding()` scans a draft for dollar amounts, document IDs, percentages, and bank digits; anything unknown is shown and **disables Approve**. It checks human edits too, which catches typos. The scorecard asserts every draft, in every tone, traces.

## 4. Agreement-aware matching

`contractPriceOn()` returns the price an agreement allows on a date, applying an escalation **only** if notice was valid. That separates:

- **PRICE_OVER_CONTRACT**: billed above the agreement → credit memo or corrected invoice.
- **PO_PRICE_STALE**: billed exactly the escalated price; our PO is old → PO change request, pay on time. No dispute.
- **CONTRACT_CONFLICT**: more than one agreement in force with different prices → escalate with both clauses. Matchbook doesn’t pick.
- **Contract sweep**: invoice = PO, so 3-way match passes, but both exceed the agreement → credit memo, plus a PO correction.

## 5. Retrieval (`retrieval.js`)

BM25 over every clause of every agreement in force, past credits, notices, carrier and portal records, and receipt notes, with one query template per finding. The top contract hit is quoted in the diagnosis; the full ranked list is in Detailed mode.

**Why BM25:** AP language is exact (“FOB Destination”, “60 days”, “credit memo”), it runs in the browser, and scores are explainable. Production would add embeddings behind the same interface.

## 6. Ingestion (`src/ingest/`)

- `pdf.js`: pdf.js (legacy build, main-thread worker) extracts positioned text and rebuilds lines.
- `parse.js`: finds the vendor by name, domain, or lookalike; pulls invoice number, date (many formats), PO, terms, remit-to, service period, notes; finds line items by searching each row for a qty × unit = amount pair, so it works across layouts. Credit memos are recognized and parsed as replies. CSV and JSON exports are supported.
- `route.js`: decides what each document is. A new bill is either clean (passes to normal approval) or an exception (added to the queue with a Bill Pay-style flag). A credit memo or a corrected invoice answers a waiting case and is verified.

`scripts/make-samples.mjs` generates the sample PDFs (three different vendor layouts) with pdf-lib.

## 7. The agent loop and MCP

`agent.js` runs the investigation as named tool calls (`docai.extract`, `match.three_way`, `match.contract_sweep`, `guard.vendor_text`, `browser.carrier_tracking`, `browser.vendor_portal`, `rag.search`, `agent.diagnose`, `policy.check`, `draft.compose`, plus the Ramp reads above). The trace is generated by the real computation, so changing a bill in the Sandbox changes the trace.

`mcp-server/server.js` exposes the same engine as MCP tools. Swapping the demo dataset for Ramp’s API is a data-layer change.

## 8. Browser automation only where there’s no API

Carrier proof of delivery (missing item receipt) and vendor portals (missing completion report). Results are evidence, never authority to act. Simulated with recorded results in the demo.

## 9. Human in the loop

- AP approves vendor-facing messages; the Controller co-signs above a threshold and owns payment holds; the budget owner approves PO changes.
- Autonomy per action type: draft only / approve / automatic. Follow-ups default to automatic once the first message is approved.
- Hard limits: payment release, bank details, and voids always need a person. A suspected bank change is verified only by phone on the number already on file; Matchbook never replies to the sender.
- “Reject, I’ll handle it” stops the agent and leaves the findings attached.

## 10. Verify, then pay

`verifyReply()` checks a credit memo’s reference and amount, or re-runs the match on a corrected invoice. A short credit memo keeps the case open and drafts a reply with the gap. Payment is released only after verification.

## 11. Cash

For early-payment terms, Matchbook computes the deadline and the discount on the undisputed amount and recommends paying that part now.

## 12. Evaluation (`evals.js`)

22 cases with expected answers: the ten seeded bills, eight parsed sample files, and three vendor replies. Checks: root cause, resolution, amount to the cent, no false dispute, citations, every draft traced, extracted fields, injection ignored, reply verdict, payment gate. Runs live on the Scorecard page (and reruns on any policy change) and in `npm test`.

## 13. Front end

React + Vite, plain CSS tokens, light theme only. Editorial design: paper, ink, one red pen for what’s wrong, Ramp’s highlighter yellow for what you can act on. Instrument Serif, Inter, IBM Plex Mono. A case reads as numbered exhibits. The tour (`src/ui/Tour.jsx`) is sequenced to avoid glitches: it waits for the target, scrolls, waits for scrolling to settle, measures, then moves the spotlight and fades the tip in; input that would scroll is held while a step is moving. `npm run build:single` produces one self-contained HTML file.

## Known limitations

- Demo dataset and simulated sends stand in for Ramp’s API and webhooks.
- Root-cause text is templated from computed facts. Unknown patterns would go to a person, not get an auto-drafted fix.
- PDFs need a text layer; scans would go through OCR first.
- Retrieval is lexical only.
